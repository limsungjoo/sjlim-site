## 맥락

목록을 받아 항목을 순서대로 실행하고, 이미 끝난 항목은 건너뛰는 기능을 만들었다.
테스트를 먼저 쓰고 구현했고, 검사기를 고장 내는 방식으로 테스트가 실제로 무엇을 잡는지도 확인했다.
리뷰까지 끝난 상태였다.

적대적 리뷰에서 아홉 건이 나왔다.
여덟 건은 고칠 수 있는 것이었다.
하나가 성격이 달랐다. 같은 목록을 두 프로세스가 동시에 실행하면 상태 파일을 확인하는 시점과 쓰는 시점 사이에 끼어들 수 있었다.

잠금을 어디에 둘지 정하려고 보니, 이미 그 결정을 내린 층이 따로 있었다.

## 선택지

| | 기존 층 | 새로 만든 것 |
| --- | --- | --- |
| 실행 범위 | 여러 노드 | 한 프로세스 |
| 상태 저장 | 공유 저장소 | 로컬 파일 |
| 재시도 | 있음 | 없음 |
| 동시 실행 | 전제 | 방어 못 함 |

- 잠금을 붙여서 둘 다 유지
- 새로 만든 것을 닫고 기존 층으로 몰기
- 기존 층을 걷어내고 새 것으로 대체

## 고른 것

닫는다.

두 개가 공존하면 "이 목록은 어느 쪽이 돌리고 있나"라는 질문이 생긴다.
그 질문의 답이 상황마다 다르면 상태를 신뢰할 수 없다.

주인이 있는 책임을 한 층 더 아래에 복제하면, 잘 만들수록 나중에 걷어내기 어려워진다.

## 버린 것

로컬 파일 기반 순차 실행의 단순함을 버렸다.
공유 저장소가 없는 환경에서 배치를 돌려야 하는 요구가 생기면 다시 봐야 한다.

리뷰에서 나온 아홉 건은 문서로 옮겨서 기존 층을 점검하는 목록으로 썼다.

되돌아보면 닫는 결정을 리뷰 뒤에 한 것도 늦었다.
"이 일을 지금 하는 곳이 있는가"는 구현 전에 묻는 질문이다.
